## 二、成员2：数据分析（进阶）

在成员1的"描述统计"之上，做老师点名的**聚类 + 关联规则**，再加一个预测模型加分项。
数据用 `06_数据/*.parquet`（读取方式见成员1交付包 `00_先读我` 第 8 章和 `02_数据字典`）。

### 任务 2.1 机场聚类画像（K-Means）
- 数据：362 个机场，特征 = 延误率、取消率、平均延误分钟、天气归因占比、log(航班量)
- 标准化后聚 4~5 类，给每类起名字（如"雷暴带休闲枢纽""高负载中转枢纽"）
- 产出：散点图（PCA 或取两个主特征着色）+ 各类中心的雷达图/表格
- 与 Figure 8 呼应：Figure 8 是人工挑 12 个枢纽看原因构成，聚类是**让算法自动把 362 个机场分类**——正好体现"进阶"。

### 任务 2.2 关联规则挖掘（Apriori，老师原话点名）
- 把字段离散化成布尔项：月份→{夏/秋/冬/春}、星期→{周末/工作日中段}、计划起飞时段→{清晨/日间/傍晚高峰}、航司类型→{低成本/全服务}、机场规模→{大/中/小}
- 用 mlxtend 的 apriori + association_rules 挖 `{条件组合} → {到达延误≥15min}`
- 报告 lift 最高、置信度最高的 5~10 条规则并解释
- 预期发现示例："夏季 + 周日 + 傍晚起飞 + 低成本航司" 组合的延误概率远超各自单独作用（lift > 1.5）——这能直接支撑成员1文档里"延误是可预测的系统负荷函数"论点。

### 任务 2.3（加分项）延误预测模型
- 逻辑回归 / 随机森林预测 ArrDel15，特征只用"计划层面可知"的（月、星期、小时、航司、机场、距离），不用事后才知道的字段（如实际滑行时间）
- 报告 AUC + 特征重要性排序，说明"延误结构性可预测"

### 工程注意事项
- 2093 万行全量跑 apriori 会很慢：先在**聚合层**做（见第四节"分析底表"），或抽一年数据
- 全部遵守成员1文档第 2 章 5 个概念 + 第 6 章 6 个雷区的口径（延误率分母=实际执行航班；原因占比分母=延误航班总延误分钟）

## 三、成员3：数据并行计算

老师要求**讲清楚：用了什么并行策略 + 为什么这么选（memory hierarchy 等）+ 有多快**。这部分的分是靠"实验对比"拿的，不是靠"代码能跑"。

### 任务 3.1 并行数据管道（核心工程）
- 用课程教的框架（multiprocessing / joblib / Dask / PySpark 任选，报告里写清选型理由）
- 把成员1的 3 个 parquet（或 36 个月的原始处理流程）做并行扫描聚合：
  按"年/月分块 → 各进程独立聚合 → 合并结果"的经典 map-reduce 结构
- 顺带论证 parquet 列存的并行优势：只读需要的列（列裁剪）+ 分块独立（无共享状态）

### 任务 3.2 基准实验（报告的重头戏）
- 固定任务：全量计算"月×小时×航司延误率"聚合
- 对比：串行 vs 2/4/8 进程；记录墙钟时间，画**加速比曲线**
- 讨论点（老师明确要看的）：
  - 为什么加到 8 进程后加速比不再线性？（内存带宽 / IO 瓶颈 / Amdahl 定律）
  - parquet 列存 vs 逐行读 CSV 的差别（memory hierarchy：顺序 IO、列裁剪减少读入量）
  - 任务是 IO-bound 还是 CPU-bound，怎么测出来的

### 任务 3.3 把成员2的分析并行化（两人的交点）
- 把 Apriori 的"频繁项集计数"或聚类前的全量特征统计放到 3.1 的并行管道上跑
- 这样报告里"并行计算"就不是孤立的 demo，而是真实分析流程的加速器——报告结构上非常顺

## 五、GitHub 仓库：放什么、不放什么

### ❌ 不要直接 push 的
- **3 个 parquet（189/185/196MB）**——GitHub 单文件硬限制 100MB，push 会被直接拒绝，历史里进了大文件以后很难清
- 原始 BTS zip/csv（共约 9.8GB）绝对不放

### ✅ 推荐的仓库结构
```
flight-delay-project/
├── README.md              # 项目简介、复现步骤、数据获取说明（写明 BTS 来源链接）
├── data/
│   ├── raw/               # .gitignore 掉，不入库；放 download 脚本让同学自己拉
│   ├── aggregated/        # ★ 入库：上面的"分析底表" csv + clean_summary.json
│   └── sample/            # 入库：抽 1 万行的 parquet/csv 样例，让人 clone 后立刻能试跑
├── docs/                  # 数据字典、口径说明（成员1交付包的 02/08 两份直接放进来）
├── scripts/               # 成员1：01_download ... 清洗、核验脚本
├── analysis/              # 成员2：聚类、关联规则、预测的 notebook
├── parallel/              # 成员3：并行管道 + 基准实验脚本和结果
├── figures/               # 8 张图（每人新增的图也放这）
└── report/                # 报告和 slides（或放 Overleaf，仓库里只放导出 PDF）
```

### 大数据文件的三种入库方案（选一个）
1. **不进 git（推荐）**：data/raw 写进 .gitignore，README 里放 BTS 官方下载链接 + 成员1的 `01_download.py`，一条命令重建数据。最干净，Canvas 提交时"datasets/links"本来就允许放链接。
2. **GitHub Release 附件**：把 3 个 parquet 打包 zip 挂到仓库的 Release 页（单文件上限 2GB），正文放下载链接。git 仓库本身保持轻量。
3. **Git LFS**：免费额度 1GB，刚好够，但每个协作的人都要装 LFS，且超额要付费——不推荐，除非老师要求仓库必须含全量数据。
