# 要素 2 ｜ 我为什么这么做（关键决策 + 一句理由）

| 决策 | 理由 |
|---|---|
| **保留全部 20,928,579 行，不删取消/备降航班** | 287,134 条取消航班和 53,309 条备降航班本身就是研究取消率、极端天气的样本，删掉这些分析就没了 |
| **用 Parquet 而不是 CSV** | 体积小 15.9 倍；Parquet 的列裁剪让"只要 5 列"的查询不必读 8.8 GB，聚合从分钟级降到 8 秒 |
| **保留全部 109 列，不裁剪成分析子集** | 其他成员可能需要备降明细（`Div1*`）等冷门字段；Parquet 下多留列的代价几乎为零 |
| **延误率的分母用"实际执行航班"（`ArrDel15 IS NOT NULL`）** | 取消航班根本没有延误时长，放进分母会系统性低估延误率 |
| **原因占比的分母用"延误航班的延误分钟"** | 五个原因字段只对到达延误≥15 分钟的航班填写，用全部航班当分母会低估到 1/5 |
| **`Cancelled`/`ArrDel15` 等由 `"0.00"/"1.00"` 转成 `0/1`** | 字符串做不了求和平均，且 `AVG()` 能直接得到比率 |
| **hhmm 时间字段用 `(hhmm // 100) % 24` 派生小时** | BTS 用 `2400` 表示次日零点（2023-06 就有 92 个起飞、365 个到达），不取模会得到 24 点这种非法小时 |
| **预计算 5 个派生列，而不是留给各人现算** | 时段、航线、周末对比是三个研究问题反复要用的，统一口径可避免每人算出不同结果 |
| **不做任何抽样** | 2093 万行全量 Parquet 下聚合只需 8 秒，没有抽样的必要，也避免了抽样偏差的质疑 |

# 要素 3 ｜ 关键结果（全是具体数字，可直接引用）

## 3.1 总量的三个基准数字

| 指标 | 数值 |
|---|---|
| 总航班数 | **20,928,579** |
| 实际执行航班数（延误率分母） | **20,588,134** |
| **到达延误率（≥15 分钟）** | **21.23%** |
| 平均到达延误 | **+7.4 分钟** |
| **中位到达延误** | **−6 分钟（提前 6 分钟）** |
| 取消 | 287,134 条（**1.37%**） |
| 备降 | 53,309 条（0.25%） |

> **"平均 +7.4、中位数 −6"这组反差是本报告最有说服力的一个数字**，说明延误是长尾结构，不能用平均数描述。

## 3.2 三个研究问题的答案

**Q1 延误的规律**

- 季节**单峰**：**6–7 月**最高（月均 29.0% / 26.7%，峰值 2024-07 = **29.6%**），秋季 9–11 月最低（低至 **13.2%**）
- **12 月不是第二高峰**（月均 21.3% ≈ 年均 21.2%，排第 7），但其内部差异极大：12/25 仅 **11.4%**，12/26–29 节后返程高达 **30–33%**（12/28 达 33.3%）——这是**需求侧拥堵**，不是天气问题
- 日内单调累积：05:00 起飞 **8.9%** → **19:00 达峰（三年均值 30.5%，2025 年最高 32.6%）**，三年曲线形状几乎重合
- 星期：**周五、周日最差**（23–24%），**周二最好**（17.9%）

**Q2 哪些机场、航司、时段最易延误**

- 航司：**F9 Frontier 29.3%** > B6 JetBlue 27.8% > NK Spirit 25.2%；最好的 **9E Endeavor 14.9%**、YX Republic 16.5%、DL Delta 17.8%
- 机场：**佛罗里达集体上榜**——FLL 27.3%、MIA 27.0%、SFB 26.8%、MCO 25.9%、PBI 24.1%；大枢纽里 **DFW 26.7%** 最差
- 时段：**19:00–20:00 起飞最危险**，05:00–06:00 最安全

**Q3 延误是什么原因造成的**（分母 = 延误航班的延误分钟，共 311,427,461 分钟）

| 原因 | 占比 | 分钟数 |
|---|---|---|
| 前序航班晚到 LateAircraft | **39.9%** | 124,146,659 |
| 航司自身 Carrier | **34.4%** | 107,011,714 |
| 空管 NAS | 19.7% | 61,415,753 |
| **天气 Weather** | **5.9%** | 18,313,928 |
| 安检 Security | 0.2% | 539,407 |

- 三年构成高度稳定，各原因波动 **≤4 个百分点**
- 极端事件是**取消**而非延误驱动的：全期最惨单日 **2024-07-19**（CrowdStrike 全球 IT 故障），单日取消 **16.5%**、延误 **58.3%**

# 要素 4 ｜ 踩过的坑和解决（可直接当报告 Discussion 与答辩弹药）

| # | 现象 | 怎么解决 | 耗时 |
|---|---|---|---|
| 1 | 这台机器 **TLS 握手是坏的**（`SEC_E_NO_CREDENTIALS`），PowerShell 的 `Invoke-WebRequest` 和 `curl.exe` **全部无法访问 HTTPS** | 换用 Python 的 OpenSSL 栈，绕开 Windows schannel | ~15 分钟 |
| 2 | BTS 跨境链路**单连接仅 0.09 MiB/s**，按此速度 0.98 GB 要下 **2.8 小时** | 实测并发曲线（4/8/12 连接），发现 8 连接是拐点，提到 **0.40 MiB/s（4.4 倍）**，实际 20 分钟下完 | ~20 分钟 |
| 3 | 沙箱**禁止命名管道**，`ProcessPoolExecutor` 直接报 `WinError 5 拒绝访问` | 改用线程池——解压是 zlib 操作会释放 GIL，仍然有效 | ~10 分钟 |
| 4 | `pip install` 无法写入 `AppData\Roaming`，被沙箱拒绝 | 改在项目内建 `.venv` 虚拟环境，顺带让环境可复现 | ~5 分钟 |
| 5 | DuckDB 的**并行 CSV reader 在 2024 年文件上报 `NotImplementedException`** | 加单线程回退分支，只有出问题的年份变慢 | ~8 分钟 |
| 6 | **BTS CSV 每行末尾多一个逗号**，标准解析会得到 110 列而非 109 列；同时发现 hhmm 字段存在 `2400` 跨夜值 | 丢掉末列；小时派生改用 `(hhmm // 100) % 24` | ~10 分钟 |
| 7 | **我最初写的 3 条图注与数据不符**：误称"丹佛天气占比高"（实际 DEN 仅 4.7%，最高是 DFW 8.1%）、误称"周一到周四递增"（实际周五/周日最差）、误称"06:00 前延误低"（00:00–04:00 红眼航班有 17–27%） | 专门写核验脚本 `14_verify_claims.py` 逐条查证并全部改正 | ~25 分钟 |
| 8 | 437 万条延误航班中，**有 18 条五个原因之和不等于 `ArrDelayMinutes`** | 逐条查出：15 条西南航空把原因全填 `0`、3 条精神航空全为 `NULL`。改 `TotalCauseDelay` 语义（五项全空时保留 NULL 而非伪装成 0）并写入数据字典 | ~15 分钟 |

> **第 7 条最值得写进报告**：它说明"先有结论再找数据"有多危险——图注是最容易被想当然填错的地方。

# 要素 6 ｜ 给写作岗的三句话

### ① 本部分最重要的一句发现

> **美国航班延误的主因是系统内部的连锁传导，不是天气**——"前序航班晚到"（39.9%）加"航司自身问题"（34.4%）合计占延误分钟的 **74.3%**，而天气被直接归因的只有 **5.9%**。

### ② 一个必须出现在报告里的数字

> **21.23%** 的航班到达延误 ≥15 分钟（分母 = 20,588,134 班实际执行航班），同时**中位到达延误是 −6 分钟**——两者并列出现，才能说明延误是"多数准点 + 少数极端"的长尾结构。

### ③ 一句可能的猜想（供写作岗展开或证伪）

> **延误率与航司的运力利用率/航班波紧凑度正相关，而非主要取决于天气。**
> 两条证据同时指向这个方向：低成本承运人系统性垫底（F9 29.3% vs 9E 14.9%，差距近 2 倍），且延误在一天内单调累积、19:00 达三年均值 30.5%（2025 年 32.6%）。
> 可进一步用 `Tail_Number` 追踪同一架飞机的日内轮转链来验证"周转时间不足导致延误沿航班波向后传导"这一机制。

| "最差机场" | 限定**起飞班次 ≥20,000** 的机场，避免小机场样本噪声 |
| 数据期间 | 2023-01-01 ~ 2025-12-31，共 36 个完整月份 |

**三个引用时容易说错的地方**：

1. 别说"天气导致 5.9% 的航班延误"——**5.9% 是延误分钟占比，不是航班占比**。
2. 别说"平均延误 7.4 分钟"就完了——必须同时给出中位数 −6 分钟，否则结论会反转。
3. 别说"119 个字段"——**官方实际是 109 个字段**，加我派生的 5 个共 114 列。
